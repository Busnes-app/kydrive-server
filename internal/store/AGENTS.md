# Storage Layer

## Purpose
Provides the unified Database Abstraction Layer (DAL) supporting pluggable backends (SQLite zero-CGO default and PostgreSQL enterprise) with automated dialect-aware migrations.

## Ownership
Owns data models, store interfaces (`UserStore`, `SessionStore`, `GroupStore`, `AuditStore`, `SettingsStore`), dialect translations, schema migrations and PostgreSQL replica coordination.

## Local Contracts
- `ApplyInstaller` creates only missing issuer-bound SCIM accounts, dedicated roles and owned configuration references; one transaction includes every ownership record and audit. Foreign accounts and drift are refused. Check/resume never create resources or audit rows. `InstallerAdministrator` identifies installer-created dedicated accounts without altering existing mixed-use accounts.
- `CompletePasswordChange` atomically compares the old password, updates any local account (a forced replacement or the owner's own change, said in the audit details), clears the flag, deletes sessions/MFA challenges, ends the account's other credentials (`drive.RevokeUserCredentials`: WebDAV passwords, agent tokens, pending computer links, service tokens and guest links; linked computers are revoked without wipe) and records `auth.password_changed`. Session/MFA issuance locks the same user row against the verified hash; MFA challenges persist the creation-time password hash, and consumption returns that snapshot to reject stale completions. Migration 4 discards preexisting challenges because their credential snapshot is unknown.
- `ResetAdminPassword` reactivates a local administrator with the replacement flag set and shares the atomic grant purge and audit path with `CompletePasswordChange`; it also works for disabled accounts.
- `SetDirectoryRole` is an explicit operator grant to exactly one active SCIM/KyIdentity subject. It accepts only admin/user, preserves directory identity, revokes sessions/MFA challenges and records the role change atomically. Local and inactive accounts are excluded.
- `RenameLocalAdmin` atomically renames only a local administrator and records an audit row. Identity, credentials and privileges stay intact; it cannot rename directory accounts or replace another account.
- `OpenInNewTab`/`SetOpenInNewTab` read and write `users.open_in_new_tab` (migration 5, default true) outside `User`, so profile, SCIM and directory updates never reset it.
- `store.Open(ctx, cfg, key)` initializes and auto-migrates the configured database backend and opens the drive store on it, in `cfg.Tenancy`. `key` is the deployment key (`cfg.Security.EncryptionKey`); the drive store refuses to open without a 32-byte key.
- SQLite runs in WAL mode with foreign keys enabled.
- PostgreSQL opens through `qmark.Open`, which rebinds `?` and `?NNN` as pgx needs, so the drive store's SQL runs unchanged; the main store's own `rebind` output has no `?` left and passes through.
- `openPostgres` holds a session advisory lock (`startLock`, on its own pool connection) while it migrates and opens the drive, so processes starting together open the schema one at a time. Locked steps (`migrations.apply`, the drive's `createPostgres`) run READ COMMITTED: a serializable snapshot would date from the lock statement, before the wait.
- Every transaction runs in `qmark.Retry`, so a PostgreSQL serialization failure reruns it (a no-op on SQLite); its body must only touch the database. A statement outside a transaction run through `Exec` reruns on its own (`qmark`'s `conn.ExecContext`): PostgreSQL rolled it back whole. A `Query` outside a transaction, `UPDATE ... RETURNING` included, does not, since its error can arrive while rows are read.
- `MigrateToPostgres` (`migrate-postgres`) copies an upgraded snapshot of a SQLite database into an empty PostgreSQL one in one transaction, table by table in `migrationTables` order, and compares each table's row count and summed row hashes before committing. `migrationTables` lists every data table in foreign-key order; a table either backend has that it does not list is refused, and `TestMigrationTablesAreCompleteAndInOrder` fails until it is added. `openedTables` are the rows a store open writes on an empty database; the copy replaces them. `sharedTables` (below) are neither compared nor copied, by the migration or the snapshot. `multiTables` (`drive_org_keys`) exist on a multi-tenant database only; a multi-tenant copy (a restored capsule, the snapshot) adds them after `drive_orgs` to the copied and opened lists (`copiedTables`, `openedIn`), so the org keys travel with the backup. Change rows keep their `seq` (the ordering trigger is off during the copy), and every identity and serial sequence is set past the copied rows. Copy errors name the table and row and PostgreSQL's message, never the driver error's detail, which can quote the row.
- `MigrateToPostgres` opens the source and creates the target in the tenancy the source records (`RecordedTenancy`; none recorded is single), so a restored multi-tenant capsule migrates into a multi-tenant schema. A multi copy disables every user trigger on the target for the copy, not only `drive_changes_in_order`: a deleted org's unpurged rows passed them when written. Single-mode copies are unchanged.
- `SnapshotPostgres` copies a PostgreSQL database into a new SQLite file in its recorded tenancy, from one REPEATABLE READ READ ONLY transaction on a one-connection pool of its own. Tables and columns must match this release's on both sides. The copy drops the file's triggers, replaces every `migrationTables` row, verifies count and row digests per table, recreates the triggers, then requires SQLite integrity and foreign-key checks and folds the WAL in. `TestPostgresSnapshotRestoresEveryRow` needs real PostgreSQL.
- `LockSQLite` is the flock on `<db>.lock` that a SQLite server holds while it runs and `migrate-postgres` takes before copying.
- Migration 13 adds `sessions.export_only` (false for existing sessions), preserved by `CreateSession`/`GetSession` on both databases. Restore reset, logout and identity revocations remove these sessions through the existing session paths.
- Migration 12 adds `sso_logout_tokens(jti, expires_at)`. `EndSSOSession` and `EndSSOSubject` take the back-channel logout token (`LogoutToken`; the zero value spends nothing) and record its `jti` until it expires in the same transaction that deletes the sessions and revokes the editor sessions, after the fence commits, so a token acts once and a failed revocation leaves it unspent for the retry; a spent one answers `ErrLogoutTokenSpent`, and expired rows are pruned on each spend (`TestLogoutTokenIsSpentWithItsRevocation`). `EndSSOSession(sid, org, fence)` with a non-empty org ends only that org's sessions and editor sessions of the sid, and returns how many it left in other orgs (`TestEndSSOSessionStaysInItsOrg`); single-tenant passes "".
- `auditSQL` records each row's org (the named account's, or NULL) on both backends.
- Local MFA is removed (two-factor sign-in is KyIdentity's). Its schema stays and no migration drops it: `users.totp_secret_enc`, `totp_enabled`, `totp_last_counter`, `recovery_codes_hash` and the `mfa_challenges` table keep their data, unused. `CreateMFAChallenge`/`ConsumeMFAChallenge` (single successful use) remain only so tests can seed and check the challenge rows that revocation paths still delete.
- `Shared` (`shared.go`, tenancy R4) is the replicas' short-lived security state, non-nil only in multi-tenant PostgreSQL: rate-limit windows (`shared_windows`, one upsert per key, `Take`/`Exceeded`/`Refund`/`Reset`), spent one-time keys (`shared_spent`, unique on kind and ID, `Spend`/`Unspend`) conversion tickets (`shared_tickets`) and the WebDAV lock table (`shared_dav_locks`, `DavLocks`: x/net memLS rules in one transaction under one advisory lock, each statement bounded at 5 s; `Confirm` weighs only the first 32 distinct presented tokens, in one query per name; a held lock never expires; migration 15). Migration 14 creates the other tables on PostgreSQL only (SQLite records the version with no DDL). Database time (`statement_timestamp()`) sets every expiry; each statement runs READ COMMITTED, since the pool's serializable default fails concurrent upserts of one key with 40001. `Sweep` (the elected worker's hourly cleanup) deletes expired rows. `TestSharedStateIsAtomicAcrossReplicas` races two stores on one key.
- `migrations.Run` applies each migration in one transaction that first excludes concurrent runners (SQLite: a no-op write takes the write lock; Postgres: `pg_advisory_xact_lock`), then checks `schema_migrations`, so processes starting together apply each version once.
- Migrations are append-only: add a version, never edit a shipped one, and give both SQLite and PostgreSQL DDL. Migration 6 drops the inherited `device_pairings` table and `users.push_device_id`.
- `ApplyDirectoryUser` is the only write path for directory input (SCIM, KySignOn webhook, SSO auto-provision). It never writes the role (new accounts are `user`), validates usernames (`ErrInvalidUsername`: 1-128 of letters, digits, `._@+-`) except when disabling an existing account, which changes only its status so a legacy username can always be switched off, touches only `scim`/`kysignon` rows, and deletes sessions and MFA challenges in the same transaction when the account ends inactive. A nonzero `Revision` (the directory's per-account version) applies only when newer than `users.directory_rev` (`ErrStale` otherwise); on an equal revision a deactivation or `DeleteDirectoryUser` applies and an activating update does not. `CreateSession` takes the MFA state the caller authenticated against and refuses (`ErrNotFound`) if it changed, inside the same transaction that checks the password hash. `RevokeDirectoryCredentials` changes no account field: for a `scim`/`kysignon` account only (`ErrNotFound` otherwise), it first commits a `kysignon` subject fence (cutoff now + 1s, `SSOLogoutFence`) so a callback holding a pre-reset ID token gets `ErrSSOSessionEnded` (`TestRevokeDirectoryCredentialsFencesPendingLogins`), then ends sessions, MFA challenges, editor sessions and every issued credential in one transaction with an `sso.mfa_reset` audit row. `EraseDirectoryUser` (multi-tenant, from `user.erased` or KyIdentity's erased list) writes `drive_erasures` and disables the subject's `kysignon` account with every grant and credential in one transaction, `ErrOtherOrg` if the account is in another org; on a multi-tenant store `ApplyDirectoryUser` then refuses to create or reactivate that subject (`ErrErased`). Moving and deleting the person's files is not built yet (tenancy design step 5). `DirectorySubject` resolves a subject KySignOn-first, then SCIM. `ListDirectoryUsers` pages SCIM accounts only.
- Migration 7 adds `users.directory_ts`, which migration 11 renames to `directory_rev` and zeroes (the webhook moved from unix seconds to revisions); migration 8 adds a unique index on `LOWER(username)`. A `Migration.Check` runs in the migration transaction first and may return `errSkipDDL` to record the migration without its DDL: v8 does so while usernames differ only by case, so an upgrade never stops on them. `Run` then calls `ensureUsernameIndex` at every start, which creates the index once no names clash and otherwise logs them; meanwhile `CreateUser` and `UpdateUser` refuse a new case variant inside the write itself (`caseVariantFree`; atomic on SQLite, not under PostgreSQL read committed), `ApplyDirectoryUser` in its transaction (`caseVariantTaken`), both `ErrAlreadyExists`, and `GetUserByUsername` and `RenameLocalAdmin` prefer the exact spelling. Nothing is renamed; the operator renames all but one (`rename-local-admin` or the directory) (`TestCaseDuplicateUsernamesDeferTheUniqueIndex`, `TestCaseVariantsRefusedWhileClashesRemain`).
- Migration 9 adds `sessions.sso_sid`, `sso_logouts` (by `sid`) and `sso_subject_logouts` (by provider and subject, with a `cutoff`; it never moves back). `EndSSOSession` and `EndSSOSubject` commit their fence before deleting sessions, and `CreateSession` checks both fences only after its insert commits, so under read committed a logout racing a login always ends it; a fenced create deletes its row and returns `ErrSSOSessionEnded`. The subject fence is keyed by subject, not account, so it also covers a first login still provisioning; like `DirectorySubject`, a `kysignon` subject also matches the SCIM account with that subject. It matches sessions by `created_at`, so it relies on SSO sessions being dated by the ID token's `iat`. Expired fences are pruned on the next call that writes one. In the same migration transaction, version 9 deletes the sessions and MFA challenges of non-local accounts (`endUnboundSSOLogins`): they predate `sso_sid`, so no logout could reach them, and the migration runs once, before any session has a `sid` (`TestBackchannelMigrationEndsUnboundSSOLogins`, SQLite and Postgres). Affected users sign in again.

- Every path that revokes an account's sessions (`revokeGrants`: password change/reset, directory deactivation, role change; plus `DeleteDirectoryUser`, `DeleteUser`, `DeleteUserSessions`, back-channel logout `EndSSOSession`/`EndSSOSubject` and sign-out `EndSession`) also calls `drive.Store.RevokeUserEditors` in the same transaction. Back-channel logout also revokes, in that transaction, the editor sessions bound to the ended login (`RevokeSSOEditors` by `sid`; `RevokeUserEditorsBefore` for each subject account by `cutoff`), even when its browser sessions were already pruned. Sign-out revokes all of the account's editor sessions: they are not bound to one browser session, and Euro-Office drops a user per key anyway.
- Every SQLite connection enables WAL, foreign keys, busy timeout and synchronous FULL even when the caller supplied other DSN pragmas. `Drive()` exposes the domain repository, never its SQL handle.
- `ReplaceGroup` writes group attributes, the complete membership set and its audit in one transaction; invalid members roll back the entire replacement. Nonempty SCIM external subjects/group identifiers are unique.

- `ResetAfterRestore` runs offline on the extracted SQLite database: one transaction removes browser/MFA grants, DAV/agent passwords, desktop credentials/codes, service tokens, organisation/guest links, editor state and unfinished uploads, randomizes file editor epochs, deletes `orgs_fresh_until` (so no customer org is served until an org poll succeeds) and `erased_since` (`ErasedSince`, so KyIdentity's erased list is read again from the start), and the private replica fingerprint and audits `system.restore_reset`. Accounts, content, direct shares, groups and integration settings stay; current directory and password changes must be reconciled before exposure. A failed transaction retains every original row.

- `UpdateReplicaConfig` is multi-mode PostgreSQL only. INSERT-if-absent then a row lock serializes independent first starts/checks/acceptance; fingerprint and explicit acceptance audit are one transaction. Malformed records and immutable deployment/device key, tenancy or staff changes fail closed. New fields merge without dropping unknown ones. `GetAllSettings` omits the private record; exact-key coordination reads retain it. Restore removes it. `TestReplicaConfigAtomic` needs real PostgreSQL.

- `WithReplicaLock` is multi-mode PostgreSQL only. A dedicated session holds a schema/name-scoped advisory lock through the callback; contention returns false without calling it. The physical session is discarded on every exit, including acquisition errors/panic, so locks never return to the pool; a held lock is unlocked first, since the server frees a closed session's lock only when its backend exits and the next owner must find it free. A one-second probe cancels the callback context on session loss; voluntary release waits for the callback to return. Callers honor cancellation, tolerate interrupted external effects, and use ordinary pool connections for their queries. Direct connections/session pooling only; transaction pooling is unsafe. Elsewhere it returns `ErrNotReplicated` without touching the database; `OnOneReplica` runs work directly then, so single-mode callers need no branch. Callers: `scheduled-worker` (`cmd/server` `startJobs`) and `backup-run` (`backup.OneRun`). A multi-mode PostgreSQL pool has at least three connections, one per lock plus queries.

## Verification
- `go test -v ./internal/store/...`
- With `KY_TEST_POSTGRES_DSN` set, `go test -race -count=1 ./internal/store -run TestReplicaLock` checks independent-pool exclusion, distinct names, release after error/panic, cancellation without premature release, backend loss and takeover. The existing PostgreSQL CI leg runs these cases; default SQLite verifies the single-mode refusal.
